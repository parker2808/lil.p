## D1 validation decisions blocking D2 wiring

- **Distinct modes, pending D1 fixer API names:** draft validation checks version, structural slots, node IDs/types, props, bounded responsive values and host authorization, but permits an empty/incomplete page without an H1 or required content. `POST /builder/activate` and `PUT /builder/draft` use **draft** validation so D5 autosave never loses an unfinished page. Publish revalidates the latest stored revision using **publish** validation, including exactly the required H1/content and host publication policy; it must reject an incomplete tree with 400 `VALIDATION_FAILED` and no version, pointer, revision bump, audit or cache change. Restore checks stored format/structure and bounded safety before mutation, but restoring a historical incomplete **draft** must not apply publish-only requirements. Do not wire both operations to the pushed `readTree` until #194 explicitly freezes their intended modes; names such as `validateDraftTree`/`validatePublishTree` are illustrative, **not current exports**.
- **Pre-parse bounds:** after a bounded JSON body is decoded and **before recursive Zod parsing**, use an iterative, cycle-safe traversal that caps serialized input at 256 KiB, node count at 500, root-inclusive depth at 5, and per-props bytes at 128 KiB (pending the corrected D1 definition). Fail closed with a typed `TREE_LIMIT`/`INVALID_TREE` result rather than `RangeError`, stack exhaustion or partial writes. Specify which slot shapes fit depth 5, including Page → Section → Row → Column → component, and revise the depth limit **together with** the slot contract if a valid composition needs more levels. D2 must also bound transport/body size and translate decode failures into existing 400 behavior; do not claim the old recursive parser is safe solely because it has a post-parse limit.
- **Responsive grid:** accept a valid `responsive.mobile.columns = 1` for single-column mobile layout even if the base grid defaults to 2–4 columns; reject unsupported values for other breakpoints using D1's corrected responsive schema and `resolveResponsive`. Never coerce one column to two or silently drop an override in a saved tree.
- **Typed HTTP mapping:** on incoming draft or publish input, map D1 `TreeResult` failures (`INVALID_TREE`, `UNSUPPORTED_VERSION`, `UNKNOWN_TYPE`, `INVALID_SLOT`, `DUPLICATE_ID`, `TREE_LIMIT`, `INVALID_PROPS`, `HEADING_RULE`) to existing **400 `VALIDATION_FAILED`** with stable `fieldErrors.tree...` and optional node ID, not a 500 or a new generic error code. For invalid **stored** tree snapshots on version read/restore, preserve existing **400 `INVALID_BLOCKS`** and `fieldErrors.snapshot` without changing bytes. Use **409 `CONFLICT`** only for stale revision/wrong mode or the server-side publish gate, not for malformed trees. Validate before CAS/mutation and keep original input available for diagnostics without logging content. Freeze exact path/status assertions with D2 controller tests after D1 lands; never mutate on rejection.

Acceptance requires empty/no-H1 draft adoption, save, reload and repeated autosave to succeed; the same draft must fail publish with unchanged raw tree/revision/rows/version/pointer/audit. Include deeply nested/oversized/cyclic (pure-function only) trees that return typed failures without `RangeError`, valid five-level nesting, mobile one-column persistence and SSR/preview parity. Future/unknown fields reject without stripping; legacy missing-SEO reads/restore still use B5b's path. DB-backed evidence belongs to a later authorized locked D2 test owner, not this docs PR.

## Observed baseline and proposed schema

`apps/api/prisma/schema.prisma:207–226` maps `Page` to `page`: it has `blocks PageBlock[]`, `publishedVersionId Int?`, and `updatedAt DateTime @updatedAt`, but no tree or revision field. `PageVersion.snapshot Json` is already non-null (`schema.prisma:228–243`) and its unique `(pageId, version)` and `Page.publishedVersionId` pointer remain unchanged. Historical migrations name the table `page` and use `DATETIME(3)` for `updatedAt` (`20261026024756_init_site`); the version migration adds JSON snapshots and the nullable pointer (`20261027120000_add_page_versions`). Millisecond timestamps can collide during rapid autosave and are also changed by unrelated page edits: **do not use `updatedAt` as the compare-and-swap token**.

Proposed **only** Prisma model diff, in `model Page` (shown as additions, not applied):

```diff
   blocks             PageBlock[]
+  draftTree          Json?
+  draftTreeRevision  BigInt       @default(0)
   versions           PageVersion[] @relation("PageVersions")
```

`draftTree` **SQL NULL** denotes the legacy `PageBlock` draft; a validated `{ schemaVersion, root }`, including an empty root, denotes builder mode. The `BigInt` revision is monotonically incremented on every tree adoption/save/publish/restore or builder metadata change, serialized as a **decimal string** in HTTP JSON (never a JavaScript number). Existing rows start at zero; a newly created legacy page is zero. Do not use JSON literal `null` as a draft or a mode; Prisma writes for legacy mode must explicitly use database null (`Prisma.DbNull`). No extra database discriminator: `PageVersion.snapshot` carries the new **tree-only** `format: "tree"` and `snapshotVersion: 1` plus `seo` and `tree` (whose own `schemaVersion` belongs to D1). Legacy snapshots remain exactly `{ seo, blocks }` without a discriminator. Reject unknown formats, unexpected fields and future versions instead of stripping or guessing legacy. Freeze this envelope's precise Zod schema after D1, before D2 implementation.

The **expected** Prisma/MySQL migration effect, illustrated rather than generated or executed here, is equivalent to:

```sql
ALTER TABLE `page`
  ADD COLUMN `draftTree` JSON NULL,
  ADD COLUMN `draftTreeRevision` BIGINT NOT NULL DEFAULT 0;
```

Prisma's actual generated SQL, column ordering and TiDB DDL support must be reviewed on a disposable environment before approval/execution; do not treat this illustrative statement as a generated migration. **Backfill: none.** No index, foreign key, table rewrite, `PageBlock` deletion or `PageVersion.snapshot` rewrite is proposed. Verify online/locking characteristics and backward read/write compatibility in a separate authorized D2 migration review; this document performs no database work.

## Authority, readers and data safety

Mode dispatch uses the database nullness of `Page.draftTree` for **draft** routes, and the explicit snapshot format for **published/version** routes. Never derive mode from a nonempty `blocks` array or combine tree nodes and `PageBlock` rows. Only explicitly eligible page keys (initially custom pages, subject to host policy) may adopt a tree; fixed Home/Hero and other portfolio pages stay legacy. Adoption is opt-in and leaves all legacy `PageBlock` rows and published versions untouched as recovery data, but those rows are **not** merged with builder content. Converting legacy blocks is D1's explicit, lossless, user-reviewed operation, not a read or migration side effect.

Keep the Nest legacy `readPageSnapshot` and B5b missing-SEO compatibility for old `{ seo, blocks }` snapshots in version detail, preview, public SSR and restore. Dispatch a `format: "tree"` envelope to a strict new reader only; unsupported formats/versions, unknown root/node keys and invalid props fail with typed errors, never fall through to the legacy parser or strip data. Admin may expose a warning/raw-safe recovery view; public routes must not start serving an unrenderable tree. Preserve unknown legacy blocks' historical public skip/log behavior and the original stored JSON. New tree versions use the same monotonic `PageVersion.version` and `publishedVersionId` pointer. A tree snapshot remains immutable when a draft is restored or edited.

An old binary will ignore the added columns for legacy pages, but cannot render a published tree envelope or safely write a builder draft. Until D3 public/preview readers are deployed and verified, builder publish is **disabled server-side**, not merely hidden in the UI. Before any binary downgrade after tree publication, either retain a compatible read-only tree renderer/reader or disable publication and explicitly export/recover every affected tree page; do not drop columns or claim that rolling back SQL restores lost content. A rollback of the D2 code before tree publication keeps the additive columns and legacy readers; a forward fix can recover retained drafts. Recovery of tree-published pages must be rehearsed on disposable data before enabling the release flag.

## Transaction and optimistic-concurrency design

- **Save/adopt:** validate payload and host authorization outside and inside the mutation boundary as needed; execute one conditional update keyed by page ID, expected `draftTreeRevision` and the correct **SQL NULL/non-NULL** mode, setting the validated tree and incrementing the revision atomically. Verify whether Prisma's nullable-JSON filter expresses this predicate unambiguously before choosing `updateMany`; otherwise use a parameterized conditional update. On affected count zero, re-read mode/revision and return 409 without writes. Return the stored revision, not a timestamp. Check revision overflow before increment. Never perform read-then-unconditional-update or silently retry on another editor's tree.
- **Publish:** after server re-validation and authorization, use **one existing Nest-owned `prisma.$transaction`**: conditional revision bump/row lock first; check affected count; re-read the current tree and SEO on the same transaction connection, verify they match the reviewed draft and expected mode; allocate `PageVersion.version`, create the strict tree snapshot, update `publishedVersionId`/`publishedAt`, write audit in that transaction. A failed validation, concurrent save, version uniqueness failure or audit failure rolls back **all** changes including the revision. Emit publish event and invalidate cache **after commit**, as the existing `page-versions.service.ts` does. The revision bump serializes concurrent publishes and invalidates a stale D5 autosave even if the tree bytes did not change.
- **Restore:** in a single host transaction, parse/validate the stored envelope **before** deleting or changing anything; compare-and-swap the current draft revision for tree-mode targets and bump it. Tree restore writes only `draftTree` and SEO (leaves `PageBlock` rows untouched); legacy restore writes `PageBlock`/SEO and SQL NULL `draftTree` with a revision bump to invalidate stale autosave, while retaining published pointer behavior. An explicit tree→legacy mode change requires a revision token; the old no-body legacy restore must not destroy an active builder draft. Existing legacy→legacy restore keeps its prior no-body contract. Audit stays in the transaction; no version is rewritten. Reject unsupported/future/unknown tree data before mutation.
- **Other edits:** any builder-relevant metadata update and publish/discard action must either participate in this CAS or be forbidden in tree mode; document the chosen host policy before D5. D5 autosave sends the last acknowledged decimal revision, retains dirty/local undo state on 409, and offers reload/manual reconciliation rather than overwriting server data. Every successful save acknowledges a new revision; failed saves do not advance it.

Failure-injection tests must assert unchanged raw JSON, revision, `PageBlock` rows, versions, pointer, SEO and audit for invalid input and transaction failure; concurrent save/save, save/publish, save/restore and publish/publish each need a deterministic loser with 409/no lost update. Include legacy snapshots missing SEO keys, unknown/future fields and known old block schema versions. Existing B1 `apps/api/test/cms-golden.e2e-spec.ts` expectations must remain unchanged. The later authorized D2 owner runs disposable-MySQL migration/compatibility/API E2E under the exclusive lock; this docs PR runs **none**. D3/D6 separately gate EN/VI, light/dark, 1440/390, WCAG AA, keyboard and public SSR/preview parity.
