1. For each listed PR, `gh pr view <number> --json headRefOid,baseRefName,mergeable,statusCheckRollup` and `git fetch origin`; record the old parent tip, last accepted SHA and current `main` SHA. Check its owner has resolved every P0–P2 (including #197's review) and its exact dependencies are landed. Never infer readiness from an old green SHA or from skipped E2E.
2. For a stacked child after its parent lands, have **the branch owner** reconstruct only its own changes on the fresh `origin/main`: `git rebase --onto origin/main <old-parent-tip> <child-branch>` when its own-commit range is unambiguous, or cherry-pick the reviewed own-commit range onto an owner-controlled replacement branch when squash/inherited sibling merges make that range unsafe. Preserve both sides of docs/lockfile/export/workflow conflicts per the rules below; regenerate Graphify after code integration. Inspect `git range-diff`, `git diff origin/main...HEAD` and changed goldens before updating the PR. Never rebase or push another owner's branch from this docs thread.
3. The owner pushes the reviewed child head with hooks enabled (`git push --force-with-lease origin <child-branch>` only if rebase requires history replacement; **never** force-push `main`), then retargets with `gh pr edit <number> --base main`. For an independent PR already based on `main`, refresh its branch against the latest `origin/main` and leave its base intact. If the parent is not merged, leave the stacked base unchanged.
4. On the **final rebased head SHA**, run `gh pr checks <number>` and inspect the linked run (`gh run view <run-id>`); require all applicable CI, security and `context` checks green, not pending, failing or silently skipped. The authorized E2E/DB/visual owner must provide serialized required evidence; this docs thread runs none. Re-check diff, mergeability and P0–P2 review resolution after every amendment; repeat checks if the SHA changes.
5. Once the final-head CI and P0–P2 gates satisfy the conditional t250u approval, an authorized owner uses `gh pr merge <number> --squash` with required checks and hooks intact. Never bypass branch protection, force-push `main`, or merge a dependent child early. Record the resulting `main` SHA; confirm the post-merge checks, Vercel/Render deploy status and `/`, `/vi`, `/api/health` before proceeding to the next child. Stop on a red or unhealthy result.
6. Before #199's migration PR, attach full D6/verification evidence against the **actual candidate including D2 schema/code and #202 route-parity behavior**, using an isolated candidate rather than merging #202 first. Parker's t250u advance merge/deploy approval remains conditional on the final-head gates; do not request it again solely because it was granted in advance. After #199, restack #202 onto its merged result, rerun final-head checks, then separately gate any publish-journey PR and final verification sign-off.
7. After any authorized deployment, sync local repositories safely: in each worktree run `git status --porcelain` first; **do not pull, reset, stash, or overwrite uncommitted work** without its owner's consent. Fetch `origin/main`, fast-forward only clean eligible local branches (`git merge --ff-only origin/main` on the appropriate branch), and have each owner reconcile and verify their preserved changes.
