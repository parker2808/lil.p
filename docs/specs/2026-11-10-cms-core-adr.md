# ADR: extract a reusable CMS core from lil.p

Status: **Coordinator-approved with required theme/visual gates** · 2026-11-10 · Inventory base: `d0d474b` (`main`)

## Plan

1. Inventory the block registry, API/page routes, editor widgets, roles, DB models, and deploy paths on `main`.
2. Define a route-complete UI standardization gate before extraction.
3. Decide the core, adapter, and portfolio boundary; define exports and budgets.
4. Specify the builder tree, migration compatibility, UX, security, and release gate.
5. Order U → B → D → verification → C; self-review and request coordinator review.

## Decision

Standardize the current UI in Phase U, then build `@parker2808/cms-core` as `packages/cms-core` in Phase B. Extract reusable contracts, pure page/block policy, and host-configurable React rendering/editing. Keep Nest, Prisma, authentication, deployment, and all twenty existing block definitions in `lil.p` for v1. The package is a library loaded by `lil.p`, not a microservice. Preserve EN/VI and current `LayoutPreset`/`BlockSurface` values. Do not change the DB schema or apply migrations in Phase B. Complete the visual builder in Phase D and verify the entire product before Phase C creates a separate private repository and switches distribution. Parker has authorized eventual private-repo creation, **not** its execution in this PR; the coordinator reviews the ADR and phase gates within the delegated scope.

Phase B preserves the current block-list behavior and contracts. The product goal is **fully dynamic page composition**: Phase D adds a visual builder in which users drag registered components into their own page layout, edit their properties, and publish without writing code. The core supplies the initial component set; host apps can register more components and provide themes. Arbitrary runtime code upload, untrusted JSX, CSS, or schema editing is outside the builder's trust model. Phase D starts only after B7 and the coordinator's design gate; it does not change the Phase B promise of zero migrations. The CMS is **not done** until builder and component-polish acceptance passes.

## Visual page builder — Phase D decision

The builder is the CMS differentiator, not a prerequisite for extracting the existing engine. Phase D introduces a **typed, versioned layout tree** and a core-owned starter component library. “Fully dynamic” means users can assemble and configure any page that the registered tree slots and component schemas allow, without a code change per page; host developers still control executable components, permissions, and design tokens.

### Model, conversion, and persistence

- The document is `{ schemaVersion, root }`. The root is a `page` node with stable opaque node IDs and ordered `section` children. A section accepts direct components or `row`/`grid`; a row accepts `column` nodes; columns and grids accept registered components. Each node has `type`, validated props, optional responsive overrides keyed by `mobile`/`tablet`/`desktop`, and declared child slots. Zod discriminated unions validate shape; the registry validates component props, allowed parent/child pairs, IDs, depth, node count, visibility, and host page policies. IDs persist through reorder, preview, publish, and restore; duplicate/copy generates fresh IDs. `schemaVersion` migrators are pure, ordered, and tested against old fixtures; unsupported future versions are rejected without rewriting data.
- **Choose an additive nullable `Page.draftTree Json?` column in Phase D**, rather than forcing a tree into one `PageBlock.props` record or introducing a node table. `PageVersion.snapshot` is already JSON: retain the legacy `{ seo, blocks }` shape and add an explicitly discriminated, versioned tree snapshot for builder pages. The existing `PageBlock` rows remain the source for legacy/fixed pages; a builder page uses `draftTree` as its draft source. A null draft tree denotes legacy mode; a validated tree, including an empty root, denotes builder mode. Snapshot format discriminates the published mode. Do not infer mode from a truthy nonempty block list, and never combine both sources. Existing `readPageSnapshot` and public/preview/version/restore handlers expect `snapshot.blocks`; D2/D3 must dispatch by snapshot format while retaining the legacy response shape and error codes. No migration or data rewrite occurs in Phase B. Adding `draftTree` requires a **Phase D additive Prisma migration and coordinator review within the delegated scope**, with a per-PR compatibility and rollout/rollback-read plan; test only on disposable local MySQL with old rows intact. Verify TiDB compatibility by reviewing supported schema/DDL characteristics, not by experimenting on production.
- Provide a pure block-list-to-tree converter for previews and opt-in adoption: wrap each old block as one section with a registered legacy-component node, preserving order, key, type, props, visibility, layout, surface, and block schema version. Use stable IDs derived from the existing block IDs/keys. Do not silently persist the converted tree or delete `PageBlock` rows; unknown block types remain lossless data with an editor warning. Portfolio Home/Hero and other fixed-page rules remain host policies and continue on the legacy path. Builder-made dynamic pages coexist with them. Reverting D2 must leave old pages readable; once a tree page is published, rollback to a pre-D binary requires an explicitly tested compatibility/recovery plan, not an assumed single-PR revert.
- Save drafts with an atomic optimistic revision check (evaluate whether `Page.updatedAt` has sufficient precision; otherwise design an additive revision token in D2); stale writes return a conflict rather than overwriting another editor. Publish validates the entire tree and creates the version snapshot plus published pointer in the existing single transaction. Restore returns a tree snapshot to the draft tree or a legacy snapshot to `PageBlock`, according to its format. Retain old routes and golden responses for legacy pages; add explicit builder routes/contracts with independently tested auth and error codes. **Keep tree publication disabled until D3's public renderer, snapshot reader and preview path pass together**; D2 may test the publish transaction without exposing tree pages publicly. Older binaries must continue reading legacy pages; tree pages require a documented recovery path before any binary rollback.

### Components, editing, and rendering

- Core starter library: section/container, row/column, and grid primitives; heading, paragraph/rich text, image, button/CTA, divider, and spacer content components. Each has a Zod prop schema, defaults, allowed slots, accessible renderer, and schema-driven property controls. Core's own neutral light/dark default theme styles these and the editor chrome even without a host theme; host apps may override tokens through the documented adapter and supply locale messages, media resolution, and optional component registrations. Portfolio collections, Hero-on-Home, project/domain widgets, and orange/green brand values remain in `lil.p`. Responsive props override a shared base at `mobile`/`tablet`/`desktop`, with explicit merge rules and bounded token choices. Avoid arbitrary CSS or script fields.
- Editor flow: drag from a categorized palette, reorder or nest only into valid slots, select a node inline, edit it in a properties panel, copy/duplicate with fresh IDs and limits, undo/redo local transactions, autosave the draft with debounce and revision conflict handling, preview, then publish through the existing snapshot/version workflow. Undo history resets only after a confirmed save/version boundary; failed autosaves retain the editable state and expose retry. Empty canvas gives a keyboard-accessible insertion action. Persisted order comes from the tree, not DOM position.
- Use the existing `@dnd-kit/*` dependency in `packages/ui` for mouse and keyboard sensors; confirm the installed licenses before moving any dependency into core, and obtain coordinator review for any new dependency. Announce picked-up node, valid destination, move, and cancellation to screen readers; provide a keyboard-only palette/insertion/reorder path, visible focus rings, 44px editor targets, and EN/VI labels. Test WCAG AA contrast and semantic heading order in both editor and published output.
- Share one registered tree renderer between authenticated preview and public output. Public pages render server-side through RSC, resolve only approved components/assets, and hydrate only components needing interaction. Lazy-load canvas, drag/drop, and property controls on admin routes. At D3 measure a standalone starter-page baseline and set a public JS budget of **zero builder/editor bytes**; keep the B3 core subpath budgets for existing consumers and record any approved revision before shipping. Compare preview and SSR output at 1440/390, light/dark, EN/VI.
- Reject unregistered types, illegal nesting, oversized/deep trees, invalid responsive values, unsafe URLs, and unsanitized rich text on the server at save **and** publish. Never execute JS/HTML from DB JSON. Check authorization for create, read draft, mutate, preview, publish, and restore separately using host capabilities; sanitize rich text and restrict media to the host resolver. Log validation failures without leaking content or credentials.
