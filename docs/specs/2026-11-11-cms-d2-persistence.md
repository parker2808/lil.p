## Contract and safety

- Only custom pages can activate tree mode; SQL NULL is legacy mode and a validated versioned tree, even empty, is tree mode. Retain legacy blocks and published versions unchanged. Tree validation uses `readTree` for incomplete drafts and `validateTreeForPublish` for publish readiness; an empty draft fails the exactly-one-H1 publish check before the D3-disabled publication conflict. A publish-ready tree still returns 409 until D3 SSR parity.
- Add `Page.draftTree Json?` and `draftTreeRevision BigInt @default(0)`; zero for existing rows, no backfill or destructive migration. HTTP revisions are canonical nonnegative decimal strings; compare-and-swap on page ID, revision and SQL-nullness prevents lost updates. Explicit JSON null is never a draft. Overflow is rejected. Invalid requests are 400 `VALIDATION_FAILED` with `fieldErrors.tree`, stale/mode mismatch is 409 `CONFLICT` including current mode/revision.
- New `GET /admin/pages/:key/builder/draft` (admin/user), `POST /admin/pages/:key/builder/activate` and `PUT /admin/pages/:key/builder/draft` (admin) accept `{expectedRevision,tree}`; `POST /admin/pages/:key/builder/publish` accepts `{expectedRevision,note?}` but always returns 409 `CONFLICT` until the D3 gate. Legacy routes/roles/response bodies remain unchanged. Existing page metadata/block mutations must not bypass the revision in tree mode.
- A future published tree envelope is `{format:'tree',snapshotVersion:1,seo,tree}` with exact keys; unknown/future input must fail, not strip. Preserve existing legacy `{seo,blocks}` reads, including missing SEO keys. Stored malformed tree restore/version requests return 400 `INVALID_BLOCKS` with `fieldErrors.snapshot`. Existing no-body legacy restore never overwrites an active builder draft; explicit revision-aware tree restore is required. Never expose an unrenderable tree on public routes.
- Revision-aware restore validates the immutable version before mutation. A tree target atomically updates only tree and SEO, leaving legacy block rows and the published pointer untouched; an explicitly selected legacy target clears tree mode and restores historical blocks/SEO. Both bump revision exactly once and audit in the same transaction. Failure leaves tree/revision/blocks/versions/SEO/audit unchanged. Tree-version preview fails closed until D3 can render it. No tree version is created while publishing is gated. Rollback before publication keeps additive columns; never drop columns with drafts or downgrade after tree publication without a compatible reader.
- Review hardening: legacy restore must compare-and-swap the page's mode and revision inside its transaction before changing block rows, so a concurrent activation cannot be cleared. Explicit builder restore rejects a legacy target containing even one unparsable block before any mutation; missing SEO keys remain readable. In tree mode, an unversioned legacy preview fails closed with a typed pending-D3 conflict instead of rendering stale rows. Disposable-MySQL tests race simultaneous saves and restore against activation and assert one winner, one conflict, and unchanged losing data.
- P1/P2 legacy-writer follow-up: legacy publish atomically claims the observed revision and SQL-NULL mode while updating the published pointer and bumping revision; a lost activation race returns 409 and rolls back the inserted version and audit. Legacy SEO updates also claim revision and mode. Block create/update/duplicate/reorder/delete use the same revision+mode CAS at the transaction's page touch, so a concurrent activation rolls back prior block writes. Publish and delete use read-committed transactions so the post-CAS conflict reread sees the winning revision. In addition to unit races, disposable-MySQL API E2E interleaves a second real connection's activation after each legacy read and asserts the 409 carries the current revision while the pointer, version, blocks and audit remain intact. Production old-instance drain remains a separate gate.
- The stacked D integration base does not yet declare core as an API runtime dependency (B5b is a separate accepted draft). D2 declares the existing workspace package and copies/builds its manifest in the API image before Nest compilation, so a production CJS import of `./tree` resolves. When integrating B5b later, reconcile its overlapping package/lockfile/Docker declarations rather than duplicating them.

## Rollback-reader gate

The disposable-MySQL pre-D2 Prisma-client regression from `350ac169` remains an explicit **known unsafe-writer reproduction**, not a safety test: an old client reads a tree page, inserts a legacy version and commits a changed `publishedVersionId` without changing `draftTreeRevision`. D2's process-local CAS cannot fence the old binary. The test is not proof of production safety; no production database was tested.

A MySQL `BEFORE UPDATE` trigger could compare `OLD` and `NEW`, but TiDB does not support triggers. A row `CHECK` cannot compare the prior pointer/revision or identify a writer; prohibiting pointers on tree rows would also break future valid publication. Neither is a portable fence for this migration. Separate DB credentials/privileges would require their own design and approval; no TiDB fence is implemented.

**Decision:** Parker approved the forward-only API policy at 08:54 ICT on 2026-11-15, not a verified write-pause/drain mechanism. Never redeploy a pre-D2 API after migration. Because the `main` Render API deployment starts `prisma migrate deploy`, pause admin page/version writes and drain _every_ pre-D2 instance before migration starts. Verify only D2-aware API instances serve before resuming page writes or activating builder drafts. If a verifiable no-overlap gate is unavailable, keep #199 blocked; a separate thread owns the proposed free-Render write-freeze guard. If D2 fails, pause writes and roll forward to a D2-aware patched API rather than reverting the API or dropping columns. A web-only rollback may leave the D2 API intact. Tree publication remains disabled pending D3 parity and release verification. Production migration and recovery still require their own authorization.
