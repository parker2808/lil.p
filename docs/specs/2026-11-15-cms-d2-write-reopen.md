# D2-aware write reopening (stacked on #199)

1. Preserve Stage A's page/version write 503 response, encoded-path and method-override handling, public health/read routes, and authenticated nonsecret deployment identity. The pre-D2 Stage A image remains always frozen in production, even with `CMS_PAGE_WRITE_FREEZE=0`.
2. The API entrypoint applies committed Prisma migrations before Node starts. Before HTTP listen, read-only queries verify the exact finished, non-rolled-back `20261111043000_add_page_draft_tree` history entry and both `page.draftTree` / `page.draftTreeRevision` physical columns. Missing history, missing columns or query failure leaves writes frozen; GET/HEAD and health remain available.
3. Only after the release owner proves the Stage A freeze and complete old-instance/in-flight-request drain and separately approves D2 may the D2-aware image deploy. With `CMS_PAGE_WRITE_FREEZE` unset or any value other than exact `1`, each new D2 instance opens writes automatically after its startup schema check; `=1` is an explicit freeze kill-switch. No Render or Vercel env change is required to reopen. The startup check does **not** prove old-instance drain or authorize rollout. Reverify instance identity, ingress, auth-bound write CAS and read-back; a public unauthenticated 503 probe cannot confirm reopening.
4. If any gate fails, keep/restore the freeze and roll forward with D2-aware code; never redeploy a pre-D2 writer. Tests cover unset/default reopen after verification, precheck/schema failure, explicit kill-switch, real AppModule middleware registration, and bootstrap ordering (`app.init()` → migration check → `listen()`), including a failed check leaving writes frozen; GitHub CI remains required on the final merged head.
