2. Exercise each of the 20 host block definitions through authenticated live API activation, CAS save/read, publish, EN/VI version preview and public JSON.

5. Run non-browser checks, regenerate Graphify, push the isolated task branch as a draft PR stacked on #202 and run exact-head ready-e2e CI. The merge chain owns all topic-branch integration.

## Editor-origin 20-type extension

1. Wire host definitions into the builder palette, composition validation, history/autosave registry and Properties descriptors without changing the neutral core or B1 golden contracts.
2. Render nested localized fields as distinct EN/VI inputs, preserve schema validation and expose a valid optional heading for definitions whose default props are empty.
3. Add four file-sharded browser groups: each creates a real page, adds one host type from the palette, edits available Properties, waits for API autosave, publishes, then compares EN/VI API and Next public/preview SSR.
4. Keep existing shard assignments unchanged and run Node 22 non-browser checks before ready-e2e exact-head CI. Distinguish host definitions with no localized editable fields (notes/projects browsers) rather than claiming edits they cannot support.

The four `cms-editor-host-{1,2,3,4}.spec.ts` files pin five definitions each to distinct shards without changing existing file assignments. Each creates a bilingual custom page, activates its draft through the real VI builder, inserts a Section, a level-1 heading when the host is not H1, searches the localized host tile and inserts it. Properties edits valid EN and VI text where defined (or `showFeatured` for the two browser types without localized defaults); the test waits for the real draft API to read the changed value, opens the Next draft route in EN and VI **before publish**, verifies the raw response host wrapper and hydrated host hash/visible edited text where the host always renders it, then publishes at its observed revision. The visible-language assertion follows D19's whole-block EN fallback when other VI fields remain blank. It compares draft/public/version-preview hashes and preview/public API JSON, plus presence of the edited text on all three browser routes for those renderers. Other hosts compare stable props and JSON, not transient streaming DOM or external-data results. This gate does not establish no-JS semantic SSR of asynchronously rendered host contents; some data-backed/empty-default hosts cannot establish nonblank semantic text from this gate alone. The existing all-20 API test remains independent. No local visual, database or production release evidence is inferred from source-only tests.

Independent exact-head review of #215 found that draft/public hash equality alone could pass if both locales resolved incorrectly. The follow-up checks each of the 20 draft host hashes against independently resolved EN/VI props and D19 effective language, checks the localized host name in the Properties inspector, and republish-tests the `hero` snapshot so `?v=1` must remain distinct from the latest public version in both locales. The remaining semantic-text limitation for data-backed hosts and no-JS SSR remains explicit; CI and a new review of the follow-up head are required.
